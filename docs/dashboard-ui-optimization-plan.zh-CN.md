# 独立站运营后台 UI 深度优化方案

> 评审日期：2026-07-30  
> 范围：`dashboard/` 当前 React 管理后台、登录页、客服收件箱、访客/工单/自动化/知识库/报表/设置。  
> 角色视角：独立站运营负责人，目标是让客服后台同时成为“转化保护、问题处置、知识运营、站点健康”控制台，而非只是一组后台页面。

## 1. 结论与方向

当前界面的问题不在于缺少功能，而在于功能以“后端能力清单”的方式平铺。用户进入系统后，无法在 10 秒内回答：今天什么影响订单、应先处理谁、哪个页面或商品正在丢失转化、AI 为什么没解决、下一步该做什么。

建议将产品定位收敛为：

> **独立站增长运营台：以异常优先队列保护转化，以客服处置保障体验，以知识和自动化降低重复成本。**

首要原则：

1. 先处理异常和机会，再浏览数据。
2. 每一页必须有明确的主要任务和下一步动作。
3. 全局站点、时间范围和状态口径必须一致且可见。
4. 高风险操作需有预览、影响范围和可恢复路径。
5. 桌面端支持高密度处置，移动端支持值班巡检和关键接管，不做桌面三栏的强行缩小版。

## 2. 审查依据与主要问题

本方案基于本地实际渲染的登录首屏及全部前端页面、交互、CSS 和 API 调用路径审查。当前本地后台依赖未完整启动，故会话数据页未能以真实数据截图复核；代码层的页面结构、状态与响应式规则均已审查。

### P0：阻断使用与信息架构问题

| 问题 | 证据 | 运营影响 | 优化要求 |
| --- | --- | --- | --- |
| 登录服务请求失败时，表单消失，只留下“请求失败 (500)” | `LoginScreen` 仅在 `providers?.email_login_enabled` 时渲染登录表单 | 任何临时接口故障都会把管理员完全锁在系统外，且无法判断如何恢复 | 保留已知登录方式；显示“重试”“检查服务状态”“联系管理员”及错误编号；仅在明确配置为禁用时隐藏方式 |
| 客户页已实现但无法访问 | `customers` 未加入 `navigationOrder`，`pageFromPath` 将 `/customers` 强制回退到 inbox | 客户历史、复购与高价值用户无法被运营使用 | 将“客户”纳入主导航；保留 URL 可直达；在权限不足时给出申请权限说明 |
| 侧栏采用“主导航 + 页面二级侧栏 + 顶部站点选择”三层结构，层级重复 | `App.tsx` 的 `primary-sidebar`、`SectionSidebar`、`topbar` | 宽度被导航消耗，操作空间不足，且站点范围不清晰 | 改为一个可折叠主侧栏；页面内用 Tabs/局部筛选承担二级导航；站点切换置于全局顶部左侧并明确作用域 |
| 报表页有独立站点过滤，和全局站点过滤不一致 | `ReportsPage` 自己维护 `siteId` | 同一用户在不同页看到的“全部/当前站点”可能不一致，数据难以对账 | 建立 `GlobalFilterContext`，全站使用同一站点、日期、时区；仅允许明确标注为“本页覆盖”的临时筛选 |
| 移动端仅移除二级侧栏，三栏会话仍有最小宽度 | `body min-width`、`.three-panel` 固定最小列宽 | 390px 宽度下核心会话工作区无法完整呈现，水平溢出或不可达 | 768px 以下切换为“队列 -> 会话 -> 客户信息”的单页栈式导航，客户信息抽屉化；不保留三栏布局 |

### P1：效率、可读性与状态问题

| 问题 | 运营影响 | 优化要求 |
| --- | --- | --- |
| 大量 9-12px 正文、标签、表格文字 | 长时间值班阅读负担大，中文扫描效率低 | 正文不小于 14px，辅助文字不小于 12px；行高 1.5-1.6；只将时间戳等次要元数据降级 |
| 主导航使用 `◫`、`◇`、`⌘`、`▥` 等 Unicode 字符 | 语义不稳定、辨识成本高、跨平台显示不一致 | 使用 Lucide 图标，保持 20px 图标和文本标签；为折叠态提供 tooltip 和 `aria-label` |
| 全局页面使用多种圆角、阴影、紫色状态、浅色卡片 | 视觉噪声高，页面像“组件样例集”，层级不稳定 | 收敛为 8px 工具卡、6px 输入与按钮、仅一层轻边框；取消无信息价值的阴影和大面积浅紫背景 |
| `styles.css` 是旧样式，`readability.css` 以约 2,491 行覆盖前者 | 同一组件的尺寸、边距、断点被多处覆盖，迭代高风险 | 拆为 tokens、base、layout、components、pages；移除重复旧规则；每个组件只由一个样式模块负责 |
| 加载、空状态、错误、无权限和禁用状态不成体系 | 运营无法判断是“暂无数据”“权限不足”“接口故障”还是“加载中” | 建立统一状态组件：骨架屏、空状态、可恢复错误、权限说明、离线提示；错误提供重试和保留上下文 |
| 固定页头、固定筛选和三列滚动容器并存 | 用户容易失去当前过滤条件与滚动位置 | 顶部固定仅保留全局上下文；队列筛选吸附在队列内；详情区独立滚动且展示当前筛选摘要 |

### P1：独立站运营视角的业务缺口

1. 首页默认是“统一收件箱”，没有“今日经营态势”。运营人员不能从一个视图看到高意向访客、结账/物流/支付异常、响应 SLA、转人工原因、CSAT 和知识缺口。
2. 报表是静态 KPI 卡和单个漏斗，缺少环比、趋势、分段和可行动的诊断。当前指标更偏系统过程，不足以指导转化保护。
3. “实时访客”只展示在线或近期消息，缺少落地页、来源、浏览深度、商品、加购/结账状态、停留时长和意图评分，无法识别应主动干预的人。
4. 会话侧栏展示大量安全与结构化字段，却没有“订单/商品/页面上下文”和“建议下一步”的决策摘要，人工处置仍要自行拼接信息。
5. 自动化采用一张四列大表单，适合配置数据库字段，不适合运营人员理解条件、预测影响、验证命中和回滚。
6. 知识库强调同步作业和底层指标，缺少“哪些问题造成转人工”“哪些商品页信息缺失”“修复后是否改善”的闭环。
7. 设置页混合账号、权限、站点、Widget、审计、备份、团队和系统状态，单页过长且角色不同的任务互相干扰。

## 3. 目标信息架构

主导航收敛为六个一级入口：

| 入口 | 首屏任务 | 核心对象 |
| --- | --- | --- |
| 概览 | 判断今日风险和机会，进入处置 | 经营异常、优先队列、关键 KPI |
| 收件箱 | 快速接管、回复、升级、解决 | 会话、工单、客户 |
| 访客与客户 | 识别高意向人群并查看历史 | 在线访客、客户档案、回访机会 |
| 内容与自动化 | 管理 Widget、知识、规则与发布 | 站点、知识缺口、规则、版本 |
| 分析 | 解释趋势，定位站点/商品/页面问题 | 漏斗、SLA、AI、CSAT、转化保护 |
| 设置 | 管理成员、权限、集成和安全 | 工作区、站点、团队、审计 |

全局顶部仅保留：工作区/站点切换、日期范围、刷新状态、通知中心、个人菜单。所有报告和列表显示“当前范围：站点 X，近 7 天，Asia/Shanghai”，避免口径漂移。

## 4. 页面级重构方案

### 4.1 概览：新增运营驾驶舱

首屏采用无卡片嵌套的三段式布局：

1. **今日优先处理**：`SLA 已超时`、`高意向待回复`、`订单/支付人工请求`、`AI 失败重复问题`，每项显示数量、最早等待时间、责任队列和“立即处理”。
2. **经营脉冲**：会话量、人工响应 P95、AI 有效解决率、CSAT、转人工率。每个指标显示与上一周期对比、趋势迷你图和状态阈值。
3. **可执行洞察**：例如“产品 A 近 24h 有 12 个尺寸问题，知识命中率低 18%”“结账页访客等待人工 9 分钟”。每条有一键进入过滤后的会话、知识缺口或自动化编辑页。

默认不显示全量数据表，异常才进入用户的注意力中心。

### 4.2 收件箱：围绕“下一件要做的事”改造

桌面端保持三栏，但改为 `280px / minmax(560px, 1fr) / 320px`，且左侧主导航可折叠以释放工作区。

**队列栏**：

- 顶部放优先分段：全部、待我处理、SLA 风险、未读、高意向、已解决；筛选收入“筛选器”按钮并支持已选条件 Chip。
- 每条会话只保留客户、渠道/站点、最后一句、等待时长、优先级和一个最关键状态；把标签压缩为 `+N`。
- 未读和 SLA 用颜色之外的文字/图标表达；排序应支持“优先级”“最新”“等待最久”。

**会话主栏**：

- 顶部固定显示：客户、当前页/商品、意图、风险、SLA 倒计时、处理归属；主操作只能有一个突出按钮，例如“接管”或“发送回复”。
- 把“转人工摘要”升级为可折叠决策摘要：客户诉求、AI 已尝试、可信证据、建议话术、禁止承诺。
- 编辑器增加模板、引用知识、插入商品链接、内部备注切换、发送状态、失败重试和快捷键提示。非归属客服回复时，明确解释“请先接管”。
- 发送后保留消息锚点、乐观状态和失败重试，不让刷新导致阅读位置跳动。

**客户上下文栏**：

- 按“本次转化相关 -> 客户历史 -> 风险和合规”排列。
- 显示来源、落地页、浏览/商品、会话次数、最近订单（仅可信身份）、偏好、历史解决方案；安全边界移至可展开“合规说明”。
- 在窄屏变成右侧抽屉，不占主会话宽度。

### 4.3 访客与客户：从监控表升级为主动运营队列

用 Tabs 区分“实时访客”“高意向”“客户档案”。

- 实时访客增加：来源渠道、当前页、商品、停留时长、浏览深度、加购/结账信号、已打开 Widget、意图和建议动作。
- 高意向规则：重复访问、高价值商品、结账页停留、运费/交付/尺码等购买阻碍、主动询问人工。
- 客户档案必须可从导航和 URL 直达，提供会话时间线、购买/咨询主题、可确认记忆和后续跟进建议。
- 禁止把未验证的访客文本包装成可信客户画像，继续沿用现有身份与记忆边界。

### 4.4 内容与自动化：改为可理解、可验证、可回滚的运营工作流

**自动化**采用规则列表 + 规则编辑抽屉：

1. 列表展示启用状态、触发条件摘要、预计命中量、最近 7 天命中/转人工/失败、最后修改者和版本。
2. 编辑采用“当...如果...则...”的分步构造器。条件与动作分区，互斥动作即时校验。
3. 发布前展示模拟样本、预计影响、冲突规则、优先级；发布后可暂停、回滚、查看执行日志。

**知识库**采用三层：知识健康总览、待修复问题、同步与发布历史。首屏展示“缺少的答案”和“受影响会话/商品/语言”，抓取范围、sitemap、向量数等放入高级诊断。

**Widget**配置提供真实尺寸的桌面/移动预览、颜色对比度校验、在线/离线/转人工/CSAT 四个状态预览和草稿与线上版本对比。

### 4.5 分析：把指标转成运营决策

将现有指标分为五个可切换主题，每个主题都支持站点、时间、渠道、语言、页面/商品、客服队列维度：

| 主题 | 必备指标 | 必备下钻 |
| --- | --- | --- |
| 转化保护 | 高意向响应率、结账页人工响应、会话辅助转化、失单原因 | 来源/落地页/商品/客服 |
| 客服效率 | 首响 P50/P95、解决时长、待办存量、SLA 违约 | 队列/客服/时段 |
| AI 质量 | 可处理问题自动解决率、转人工原因、引用覆盖率、重复提问率 | 意图/知识源/商品/语言 |
| 客户体验 | CSAT、评价覆盖率、复联率、负反馈主题 | 站点/客服/问题类型 |
| 内容健康 | 知识缺口数、修复时长、修复后转人工率变化、商品信息新鲜度 | 页面/商品/知识版本 |

规则：不展示没有对比、阈值或下钻入口的 KPI 卡；每个异常图表都要提供“查看受影响会话”。

### 4.6 设置：按职责拆分

将当前单页改为左侧设置导航：`工作区与站点`、`团队与权限`、`Widget 与连接器`、`安全与会话`、`审计与备份`。平台租户管理只给平台角色显示，且独立于日常客服设置。所有敏感操作使用确认弹窗，标明影响范围与审计记录。

## 5. 视觉与交互规范

### 5.1 设计令牌

- 字体：`Inter, Noto Sans SC, Microsoft YaHei UI, sans-serif`；不混用同等权重的多种英文字体。
- 字号：页面标题 24px，区块标题 16px，正文 14px，辅助文字 12px，标签 12px；拒绝 9-10px 关键文字。
- 间距：4px 基准，区块 24px，组件内部 12/16px；使用固定节奏而不是逐页微调。
- 圆角：输入、按钮 6px；工具面板与列表单元 8px；不要使用 14-20px 的“营销卡”圆角。
- 色彩：中性白/灰为主体；蓝用于主操作与链接，绿/橙/红只表达成功、风险和阻断。不能只靠颜色传达状态。
- 图标：统一 Lucide；操作按钮优先图标并带 hover tooltip，主命令使用图标加文本。

### 5.2 可访问性与操作效率

1. 对比度达到 WCAG AA；颜色状态额外搭配文案和图标。
2. 全部交互有可见焦点、键盘可达、语义标签和 44px 最小触控区域。
3. 支持收件箱快捷操作：`j/k` 切换会话、`r` 回复、`n` 内部备注、`a` 接管、`e` 解决；仅在输入框未聚焦时触发。
4. 删除、发布、回滚、撤销会话等操作必须确认，且可明确撤销的操作提供 Undo。
5. 所有异步写入显示进行中、成功、失败和重试，不将 API 原始状态码作为终端用户主要文案。

## 6. 响应式策略

| 宽度 | 形态 | 关键规则 |
| --- | --- | --- |
| >= 1440px | 完整桌面工作台 | 可显示三栏收件箱、两列分析；主导航可收起 |
| 1024-1439px | 紧凑桌面 | 收起主导航标签；客户栏默认抽屉；表格允许列选择而非整体挤压 |
| 768-1023px | 平板值班 | 左侧队列 280px + 会话主栏；上下文以抽屉呈现 |
| < 768px | 移动巡检 | 底部主导航；会话、访客、告警为单栏；不渲染桌面三栏/宽表格 |

移动端优先保证：查看告警、筛选待办、接管会话、快速回复、升级工单和查看客户关键信息。站点管理、复杂规则编辑和审计表放到只读摘要或明确提示“请在桌面端完成”。

## 7. 实施路线与优先级

### 第一阶段：消除阻断与统一骨架（1-2 周）

- 修复登录失败状态、保留重试路径；补齐客户导航与 URL。
- 建立全局站点/时间范围上下文，移除报表局部口径分叉。
- 将 CSS 拆分为 tokens/base/layout/components/pages，删除 `readability.css` 覆盖层。
- 更新图标、字号、焦点、按钮层级、统一状态组件。
- 完成 390px、768px、1024px、1440px 的页面级响应式验收。

### 第二阶段：重构核心日常流程（2-4 周）

- 新增运营概览，重做收件箱优先队列、决策摘要、客户上下文抽屉和快捷回复。
- 建立访客/客户一体化视图，并补齐高意向字段和筛选。
- 重构设置导航，避免把所有治理能力堆在一个长页面。

### 第三阶段：建立增长闭环（3-5 周）

- 自动化规则构造器、模拟测试、影响预览和版本回滚。
- 知识缺口到修复、发布、效果回看闭环。
- 新分析中心和异常到受影响会话的下钻。

## 8. 技术落地建议

1. 引入 `lucide-react`、可访问的 Dialog/Popover/Tooltip 原语（可采用 Radix），不手写 Unicode 图标和不可控弹层。
2. 用 React Context 或 URL query 参数承载全局 `tenant/site/date/timezone`；可分享的筛选需序列化到 URL。
3. 收件箱、访客、工单和日志全部采用服务端分页、稳定排序和虚拟列表；前端不应一次加载全量会话后过滤。
4. 将页面组件按领域拆分，建议结构：`features/inbox`、`features/visitors`、`features/knowledge`、`features/analytics`、`features/settings`、`components/ui`、`styles/tokens.css`。
5. 增加视觉回归：Playwright 截图覆盖登录、概览、收件箱、规则编辑、知识页，视口 390/768/1440px；同时覆盖加载、空、无权限、失败和成功状态。
6. 所有运营写入继续通过现有应用服务与幂等接口完成；UI 不绕过服务层，不信任浏览器输入中的租户或身份。

## 9. 成功标准

### 体验验收

- 运营能在 10 秒内识别“最需处理的三类事项”，在 3 次点击内打开对应会话。
- 客服在 30 秒内完成“识别上下文 -> 接管 -> 使用模板/证据回复 -> 解决或升级”。
- 390px 至 1440px 不出现不可达内容、横向截断、文本重叠或依赖悬停才可发现的操作。
- 主要任务的加载、空、错误、无权限、成功状态均可区分，且错误均可恢复或给出下一步。

### 运营指标（上线前设基线，上线后按周复盘）

| 指标 | 目标 |
| --- | --- |
| SLA 超时会话占比 | 下降 25% |
| 高意向访客首次人工响应 P95 | 下降 30% |
| 人工单次处理耗时 | 下降 20% |
| 知识缺口从发现到关闭时长 | 下降 30% |
| CSAT 评价响应率 | 提升 15 个百分点 |
| 运营异常下钻使用率 | >= 60% |
| 桌面/移动关键任务成功率 | >= 95% |

## 10. 不应做的事

1. 不以渐变、更多卡片、更多颜色替代信息架构重构。
2. 不把桌面三栏等比例压缩到手机端。
3. 不把安全、风险、审计文案从系统移除；应将其放在操作决策点，而不是占据日常阅读空间。
4. 不为了“运营化”让 UI 绕过现有租户、身份、权限、幂等和人工审批边界。
5. 不在没有事件数据、订单归因和可信身份前声称精确“会话转化率”；先定义事件口径和数据质量标识。
