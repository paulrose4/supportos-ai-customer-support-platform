## 2. 项目与个人职责的关系

SupportOS 是在职期间面向公司真实业务开发的内部系统。它不应被理解为个人业余项目，也不以个人名义
主张公司业务数据或知识产权归属。项目的需求拆解、系统设计、核心代码、前后端集成、自动化测试、部署
与维护由本人独立完成；客服和运营团队是业务需求与实际使用反馈的来源。

公开仓库用于展示经过授权的工程实现和可复现证据。仓库中的个人贡献说明描述的是实际工程职责，
不等同于对代码知识产权归属作额外声明。

## 3. 为什么公开仓库从代码快照开始

原始开发历史包含不适合公开传播的内容，例如真实业务语境、内部配置、运营材料、早期原始评测结果和
个人求职文件。即使这些内容已经从最新代码中删除，它们仍可能存在于旧 Git 对象、分支或 Pull Request
引用中。

因此，公开发布没有伪造或人为拆分历史提交，而是采用以下流程：

1. 从内部项目的已验证代码版本建立独立发布工作树。
2. 移除真实客户 PII、密钥、私有运营数据、生产标识符和个人材料。
3. 使用合成域名、SKU、商品、政策与 Eval 检索语料替换公开示例。
4. 重新执行代码质量、架构契约、自动化测试、前端构建和离线回归。
5. 使用全新的根提交创建公开仓库，原始开发历史继续保持私有。

因此，公开仓库的初始提交日期和提交数量代表公开发布过程，不代表项目的完整开发周期。从公开发布之后
开始，修复、文档、评测和功能演进将按真实提交持续记录。

## 4. 公开内容边界

| 公开内容 | 保持私有或移除的内容 |
| --- | --- |
| 经授权的应用源码、迁移、测试和部署基线 | 客户 PII、真实订单、邀请记录和内部运营数据 |
| 脱敏产品截图 | 敏感垂直业务内容和可识别的工作区信息 |
| 合成商品、政策、域名、SKU 与 Eval 数据 | 生产密钥、真实环境变量和基础设施细节 |
| 架构、工程案例、质量命令和已知边界 | 个人简历、面试材料和旧模型原始输出 |

公开仓库没有声明未经验证的 Recall@10、真实模型效果、P95 延迟、成本、自动解决率或 CSAT。此类指标只有
在绑定当前 commit、数据集哈希、模型配置与目标环境重新运行后，才会作为公开证据。

## 5. 当前可复现基线

公开版本使用以下质量门禁：

```bash
python -m ruff check .
python -m ruff format --check .
python scripts/check_architecture.py
python -m pytest

cd dashboard
npm ci
npm test
npm run build
```

当前仓库记录的基线包括：默认环境 751 项 Python 测试通过、30/30 Dashboard 测试通过、30/30 固定离线
输出合同回归通过，以及 6/6 架构契约通过。另有 55 项 PostgreSQL、Qdrant 和 Redis 集成测试需要在目标
基础设施环境执行，不能把默认跳过理解为失败或本轮已经完成真实基础设施验收。
