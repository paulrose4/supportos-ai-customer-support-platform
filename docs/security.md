# Security Architecture

## 1. Security Objective

Protect tenant boundaries, customer identity, business facts, knowledge integrity, and personal data while ensuring the agent fails closed. The model is an untrusted probabilistic component: it may propose classifications or language but cannot grant access, choose tenants, approve actions, override deterministic policy, resolve material policy conflicts, or invent business facts/SLA promises.

## 2. Trust Boundaries

1. Client to FastAPI: all request content and headers are untrusted.
2. Trusted gateway/auth adapter to application: only verified identity is converted to `AuthenticatedPrincipal`.
3. Application to LangGraph: minimum authenticated context and channel-neutral DTOs only.
4. Application to business repositories: tenant, scope, ownership, and freshness are enforced before returning minimum DTOs.
5. Vault to ingestion: Markdown and frontmatter are untrusted content requiring schema, path, size, publication, and policy validation.
6. Application to model/embedding provider: data is minimized and redacted; provider responses are untrusted until schema and policy validation.
7. PostgreSQL to Qdrant: only approved knowledge projection crosses the boundary; customer/business data is prohibited.
8. Agent to human queue: handoff context is redacted, evidence-linked, tenant-scoped, and idempotent.

## 3. Authentication and Authorization

- Development `MockPrincipal` is available only under explicit non-production configuration and is generated by a dedicated adapter.
- Production startup must fail if mock authentication is enabled.
- JWT verification validates signature, issuer, audience, time claims, and configured authentication policy before principal construction.
- Gateway-derived headers require authenticated gateway provenance; arbitrary client identity headers are discarded.
- `AuthenticatedPrincipal.tenant_id` cannot be overridden by request body, message text, graph output, model output, query parameter, or tool argument.
- Authorization is deny-by-default and evaluates role, scope, tenant, resource ownership, operation, and risk.
- Anonymous requests receive an anonymous principal with public-only capability, not a fabricated customer identity.
- Repeated authentication failure and inconsistent identity signals are Risk 3 events.

## 4. Tenant Isolation

- Every tenant-owned relational record includes `tenant_id`; important unique and foreign-key relationships include tenant context.
- Repository interfaces require tenant context and reject empty tenant IDs.
- Background jobs use trusted service tenant configuration and process one tenant scope at a time.
- Qdrant filters for tenant and audience are assembled in the adapter/application layer and cannot be supplied solely by the LLM.
- Cache keys include tenant, resource, authorization-relevant context, and version.
- Logs, metrics, traces, queues, and audit events retain tenant attribution without exposing sensitive tenant data.
- Tests use two tenants with overlapping customer/order/document IDs and verify no read, retrieval, cache, write, trace, or handoff crossover.

## 5. Knowledge Supply-Chain Security

- Vault paths are rooted in configured directories; traversal, unsafe symbolic-link escapes, unsupported binary content, and oversized files are rejected.
- Frontmatter uses an allowlisted schema. Unknown security-sensitive fields cannot silently override trusted metadata.
- Tenant synchronization scans only `TENANT_KNOWLEDGE_ROOT/{tenant_id}/obsidian`; sibling tenant directories are never enumerated.
- `tenant_id` in frontmatter must match the trusted synchronization and directory tenant; a mismatch is quarantined as excluded and is never embedded or indexed.
- Saving is not publishing. Only validated, effective, reviewer-compliant `published` versions become active.
- Draft/review/archived content is excluded by trusted retrieval filters.
- Document text is evidence data, never system instruction. Instructions inside documents cannot alter tools, permissions, filters, policies, or graph routing.
- High-risk policies require reviewer metadata and reviewed target-language content.
- Material conflict creates an auditable record and forces handoff; vector score cannot choose a winner.
- Content hash, parser/chunker/embedding versions, source path, and publication transition are audited.

## 6. PII and Model Data Policy

- `PiiRedactorPort` runs before all chat-model calls, including classification, query rewriting, drafting, judging, and handoff summarization.
- Tool results are mapped to minimum DTOs before graph state or prompts.
- Allowlisted model fields are masked order ID, product/SKU/specification, status, policy region, sanitized question text, and non-reversible correlation ID when needed.
- Tokens, credentials, full identifiers, full contact/address data, biometrics, payment data, other-customer data, and unnecessary names are prohibited.
- Logs record allowlisted metadata and hashes, not complete objects or prompts.
- Model output passes outbound PII, cross-customer, tenant, grounding, commitment, and SLA validation.
- External and private models use the same minimization contract. Provider location and data policy are configuration reviewed before launch.
- Raw model requests are retained at most 30 days by default and only when explicitly enabled; redacted traces are preferred.

## 7. Risk Policy and Safe Actions

| Risk | Automated capability | Mandatory controls | Terminal behavior |
|---|---|---|---|
| 0 | public answer | published/public/effective/tenant evidence; grounding validation | answer or handoff on insufficient/conflict |
| 1 | authenticated read-only answer | verified identity, tenant, ownership, fresh source, no mutation | answer or handoff on failure/staleness |
| 2 | collect minimum information; create pending request | fresh authoritative facts, deterministic policy, no irreversible tool | human approval required |
| 3 | no continued automated handling | minimize data and response; preserve audit evidence | immediate human/security handoff |

The deterministic rules engine sets the minimum risk. Model signals may increase review but cannot reduce policy risk.

## 8. Tool Security

- Tools are registered by allowlist. MVP exposes read-only business tools plus controlled persistence/handoff tools.
- Tool arguments are constructed from trusted principal, validated entities, and application policy; the model cannot supply tenant or customer ownership assertions.
- Every tool call records tenant, principal subject, scope decision, sanitized input, result status, latency, source/version, and trace ID.
- Timeouts, provider errors, malformed results, tenant mismatch, ownership mismatch, and stale facts fail closed.
- No real refund, cancel, address, payment, compensation, privacy execution, or irreversible operation is registered.
- Future write tools require idempotency key, fresh authoritative read, optimistic version check, explicit permission, audit, bounded transaction, and human approval according to risk.

## 9. State, Checkpoint, and Replay Security

- State is bounded, JSON-safe, versioned, and contains no token, secret, session, ORM object, SDK response, exception object, or full unrestricted history.
- Checkpoint storage is treated as sensitive conversation data and follows retention/access policy.
- State business facts carry `fetched_at`, `source`, and `version/etag`; they are evidence snapshots, not current authority.
- Risk 2 decisions and all future mutations re-query authoritative systems after resume.
- Side effects use deterministic idempotency keys so retries/replay do not duplicate messages, conflicts, pending requests, handoffs, or audit events.
- A resumed run revalidates principal freshness, tenant, authorization, source freshness, and publication eligibility where relevant.

## 10. Write Controls

| Write | Idempotency | Permission | Audit | Transaction | Approval |
|---|---|---|---|---|---|
| conversation/message/run | external message/run key | channel/agent service | actor, tenant, trace | short PostgreSQL transaction | none |
| handoff/pending request | tenant+conversation+run+reason key | agent service | reason, evidence, failures, SLA | handoff and queue atomically | human for subsequent action |
| knowledge version | document+content hash | sync worker | source and parser versions | immutable version transaction | high-risk publish reviewer |
| conflict record/resolution | conflict fingerprint/version | knowledge service/reviewer | affected versions and decision | bounded PostgreSQL transaction | authorized reviewer resolves |
| vector projection | deterministic point/operation ID | vector service account | manifest and counts in PostgreSQL | eventual consistency | large rebuild/deletion operator review |
| purge | tenant+policy+run key | privacy/admin service | policy, actor, counts | bounded batches | approved production workflow |
| real business mutation | not present in MVP | prohibited | attempted use is security event | none | mandatory future design |

Mandatory audit failure blocks high-risk automated completion. Audit records are append-oriented and separately retention-controlled.

## 11. Freshness and Cache Security

- Authentication and authorization are never sourced from ordinary business caches.
- Risk 2/3 and future write/eligibility operations always perform a fresh authoritative read.
- Risk 1 order status may use a maximum 30-second cache containing `fetched_at`, `source`, and `version/etag`.
- Cache keys include tenant and resource ownership context.
- Expired, unverifiable, mismatched, or unavailable data cannot be described as current.
- The application service decides cache use; model prompts cannot request bypass or extension.
- Public knowledge caching respects publication, version, effective interval, and tenant/audience invalidation.

## 12. Retention and Deletion

- Retention periods are configured by data class and reviewed before production.
- Purge jobs are authorized, tenant-scoped, idempotent, auditable, resumable, and batched.
- Tokens and secrets are never persisted; temporary embedding content is not separately retained.
- Customer deletion design must cover business records according to legal policy, conversations, tool results, model traces, handoffs, and audit pseudonymization/retention exceptions.
- Qdrant contains no customer-derived vectors in MVP, simplifying customer deletion.
- Legal hold is not implemented in MVP; production purge must not launch until the organization confirms whether it is required.

## 13. Threat Scenarios and Required Outcomes

- User says “I am customer X”: ignored as identity; trusted principal remains authoritative.
- User supplies another tenant/order ID: ownership/tenant rule denies and records a security event.
- Prompt injection in message or Vault asks to ignore policy: treated as data; tools and routing remain unchanged.
- Qdrant returns another tenant due to adapter defect: post-retrieval tenant invariant rejects all results and raises P0 alert.
- Business tool times out: no guessed status; handoff or safe retry policy.
- Published policies conflict: create conflict record and handoff.
- Model invents refund/SLA/amount/deadline: deterministic validator rejects; one constrained repair maximum, then handoff.
- High-risk policy exists only in unreviewed translation: handoff.
- Graph replay repeats handoff node: idempotency returns the existing handoff.
- Audit persistence fails during Risk 2/3 flow: block automated completion and raise operational alert.

## 14. Security Verification

Required suites:

- authentication spoofing and mock-auth production-disable tests;
- cross-tenant repository, vector, cache, trace, queue, and purge tests;
- ownership and object-enumeration tests;
- prompt/Vault injection tests;
- PII redaction and outbound leakage tests;
- stale data and source outage tests;
- conflict and authority tests;
- replay/idempotency tests;
- prohibited tool registration tests;
- Risk 0-3 routing and mandatory-handoff evals;
- model/provider failure and malformed structured-output tests.

## 15. Known Pre-Production Review Items

No current architecture decision introduces an unresolved P0/P1 blocker. Before production, security/privacy/legal owners must finalize JWT/gateway trust configuration, retention/legal-hold policy, provider region/data-use terms, PII classification, high-risk reviewer roles, and handoff/security queue ownership.
